## 0. Why, method, and what changed in scoping

**Founder request (Wyatt, 2026-10-05).** Review the app code base the way DHH would: find duplicate code, unused code and the inconsistencies between copies that cause corner-case bugs; turn the findings into scoped work on the roadmap; then execute it. The first package took the client. This package takes the server, the API and the tooling.

**Method.**
1. **Seven Fable reviewers, one area each.** The verified issues that survived carry five prefixes: **B1** (`backend/src` feeds, catalog, identity, narration types), **B2** (`backend/src` cost, config, curation, enrichment, CLIs, migrations, README), **A1** (`api/` handlers and `api/_lib`), **T1** (`tools/` data pipeline: refresh, shows, classify, poll, harvest, foraycorpus-export) and **T2** (`tools/ci`, `tools/release`, `tools/mobile`, `tools/web`, `.github/`). Each reviewer filed issues with id, category (duplicate / dead-code / inconsistency / duplicated-state / stale-comment / drift-risk / needless-complexity / corner-case-bug), severity, locations, evidence, a failure scenario and a fix.
2. **Separate Fable verifiers** reproduced every claim from the source (`git grep`, `node -e` over the data files, reading both sides of each duplicate; T2-04 was reproduced on this Windows machine through a junction). Each issue carries a verdict: `confirmed` (every claim held) or `adjusted` (a claim was wrong or overstated; the record says which and the severity was moved). Issues the verifiers refuted outright were dropped before scoping. **89 issues survived**: B1 14, B2 19, A1 13, T1 23, T2 20. By severity: 8 high, 35 medium, 46 low. The full list is Appendix A.
3. **A Fable scoper** grouped the 89 into cards — one agent, one PR each — ordered into waves so that no two cards in a wave touch the same file. Every card opens with characterization tests that pin today's behaviour before anything moves, then adds tests whose named mutation goes red. Workflow and composite edits compile only in CI. Five issues were deferred as founder rulings rather than engineering (§5); the critic moved a sixth there.
4. **A Fable critic** read the scoping against the code and returned 20 amendments. **18 were checked against `43446c00` and accepted; 2 were rejected in part**, with the reason in §0.3.

**UI freeze.** No card touches `app.js`, `styles.css` or `index.html`. The two client halves the review found (B2-08's `SB_USER_TABLES` set-equality test; A1-03's `k` parameter on in-show search) are deferred for that reason and named in §5.

**Result: 43 cards in 8 waves**, 31 opus and 12 qwen, and 6 deferred rulings. Wave 1 (23 cards) carries every bug-risk item. Waves 2–6 serialise the `api/` handler work (every card there touches `api/episodes/search.ts` and `api/shows/[show_id]/episodes.ts`, which the no-shared-file rule forbids in one wave): one catalogue loader, one show resolver + one episode identity, one feed/search cache policy, one Apple client, then handler hygiene. Waves 7 and 8 are the entry-guard sweep alone, split by subtree, because it touches a one-liner in ~100 `tools/` CLIs.

## 1. Goal, done-definition, dependencies, founder questions

**Goal.** One rule, one place: every duplicated rule in the backend, the API and the tooling has a single owner that the copies import or pin to; dead code and false comments are gone; the corner-case bugs the duplicates caused are fixed; and every change is behaviour-preserving except the listener-visible fixes named in §0.2 and the deliberate decisions each card states.

**Done when.** Every card's PR is merged (wave by wave, in order); `node tools/ci/run-suites.mjs`, `cd backend && npm test && npm run typecheck` and `npm --prefix api test && npm --prefix api run typecheck` are green with every floor raised to the true count; the six §5 deferrals each have a founder answer recorded (in `HUMAN-ACTIONS.md` as `[DECIDE]` items, or `docs/DECISIONS.md` by the founder); and Appendix A's 89 ids are each either closed by a merged card or deferred by a ruling.

**Dependencies.**

## Standard conventions (every card applies these verbatim)

- Repo: `C:/Users/wjduv/Desktop/Vibe Coding/foray`. Start: `git -C "<repo>" fetch origin` then `git -C "<repo>" -c core.autocrlf=false worktree add C:/w/<card-id> -b refactor/<card-id>-<slug> origin/main` and work ONLY in that worktree (LF tree; never run `format:write` repo-wide; never `git restore`/`git clean`; never work in the founder checkout).
- **Characterization first.** Every card's first commit adds the tests that pin today's behaviour (named in the card under "Characterization FIRST") and they pass against the unmodified code. Only then does the refactor land. A reviewer must be able to see the pin before the move. Where the card says a pin is "RED today", that test is the bug's reproduction: it is committed red in commit 1 with a `// RED on main: <issue>` comment and flips green with the change.
- **Mutations.** Every new test's comment names the one-line mutation that turns it red, and you run that mutation once before committing.
- **Floors are minimums.** `test/suite-integrity.test.js` asserts `count >= floor` and scans `player/`, `test/`, `tools/` recursively plus `backend/test` (`BACKEND_FLOORS`). A NEW suite under those trees needs a floor entry with its top-level test count in the same PR. When a suite grows by N, raise its floor by N and append `; <old> -> <new> // CH2-xx: <what>` to that line's comment. When a card DELETES tests, set the floor to the exact new count and say so. Never delete a test to hit a number. `api/_test` is not scanned: api suites have no floor.
- **Runners.** Backend: `cd backend && npx vitest run <file>` and `npx tsc --noEmit` (every backend card runs both packages' typecheck: `cd api && npx tsc -p tsconfig.typecheck.json` too, because `api/` imports `backend/src`). API: `npm --prefix api test` (`node --import tsx --test "_test/**/*.test.mjs"`). Tools: `node --test <file>`. CI-equivalent full run: `node tools/ci/run-suites.mjs` (once before the PR). One test process at a time.
- **Bundle guards.** Any card touching a file under `backend/src/feeds`, `backend/src/catalog` or `api/_lib` runs `node --import tsx --test api/_test/import-closure.test.mjs api/_test/vercel-bundle.test.mjs` and quotes them green: those two tests are what stands between a new import and a `FUNCTION_INVOCATION_FAILED` in production.
- **Line numbers are hints.** Re-locate every cited symbol on `origin/main` with `git grep` before editing; a missing symbol is a stop condition.
- **UI freeze.** No card touches `app.js`, `styles.css` or `index.html`. `sw.js` `BUILD_ID` stays the literal `"unstamped"`. Never commit `deploy-manifest.json` or `data/forays-directory.json`. `test/data-deletion.test.js`, `test/legal-citations.test.js` and `test/supabase-verify-applied.test.js` stay green untouched.
- **Migrations.** 0020 is reserved (shows-search PKG-10). This package adds 0021 only (CH2-01). Applied migrations are never edited; corrections to their comments go in code notes.
- **Workflows compile only in CI.** A card that edits `.github/` dispatches or lets run the affected workflow on the PR branch once and quotes the run URL in the PR.
- Commit messages end with the trailer lines your harness gives you (`Co-Authored-By:` + `Claude-Session:`). PR opened as DRAFT (`gh pr create --draft`), title `refactor(<area>): <card title> (CH2-xx)`, body opens with a 1–2 sentence TL;DR then `---`, lists the issues closed by id, names every characterization test and every mutation run, quotes the bundle guards and CI runs where required, and ends with `🤖 Generated with [Claude Code](https://claude.com/claude-code)` and the session URL line. Open the PR and STOP. Never label, never merge.
