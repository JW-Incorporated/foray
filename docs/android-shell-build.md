# The Android shell — the build, and the CSP question it was built to answer

Issue **#37**, part of **#34**. Reads on from `docs/mobile-shell.md` (#36, the
scaffold) and `docs/research/mp1-background-audio.md` (#35, the spike).

Android was the last unbuilt platform. `mobile/android/` had never been
generated from this repo; `docs/mobile-shell.md` §5 named Capacitor's injected
bridge versus our strict CSP as **the top open risk**, unproven in either
direction, and #213's iOS workflow says in its own header that this risk *"is
Android's, by a different mechanism, and stays open"*.

It no longer is. It is answered below — **by source, not by execution**, and §3
says exactly what that is worth.

## 1. The build

### 1.1 It builds

Both configurations, from a clean `cap add`:

| | Result | APK | Wall clock |
|---|---|---|---|
| `./gradlew assembleDebug` | **BUILD SUCCESSFUL** | `app-debug.apk`, **4,932,485 bytes** (4.70 MiB) | 18 m 03 s, cold Gradle cache, 213 tasks all executed |
| `./gradlew assembleRelease` | **BUILD SUCCESSFUL** | `app-release-unsigned.apk`, **3,852,273 bytes** (3.67 MiB) | 10 m 48 s, warm cache, 53 of 283 tasks executed |

`assembleRelease` runs `lintVitalRelease`, which is the lint pass that can fail a
release build on its own, and it passed. The APK is **unsigned**: there is no
keystore in this repo and no Play account, so `app-release-unsigned.apk` is the
correct and final artefact of a build here. Signing is a founder action.

**One failure worth recording, because it was mine and it looks like a toolchain
bug.** The first `assembleRelease` attempt **failed** after 13 m 29 s at
`:capacitor-cordova-android-plugins:mergeReleaseResources`:

```
Cannot access output property 'incrementalFolder' of task
':capacitor-cordova-android-plugins:mergeReleaseResources'.
  > java.nio.file.NoSuchFileException: …\capacitor-cordova-android-plugins\build\
    intermediates\incremental\release\mergeReleaseResources\merged.dir\values-xlarge-v4
```

wrong with either number; they are different apps.

**Two traps MP1 recorded, both still real, both still costed:**

- **Capacitor 8 requires JDK 21.** JDK 17 dies at

  `JAVA_HOME` at it.
- **`local.properties` is a Java properties file**, so `sdk.dir` must use forward

  `mobile/android/local.properties` is gitignored, so every machine writes its own.

### 1.3 The lockfile, and a claim in §0 of `docs/mobile-shell.md` that was never true

`docs/mobile-shell.md` §0 and `mobile/README.md` both said all seven
`@capacitor/*` packages *"resolve to **8.5.0**"*, from a registry check with
nothing installed. An actual `npm install` resolves:

| Package | Resolved |
|---|---|
| `@capacitor/core`, `@capacitor/cli`, `@capacitor/android`, `@capacitor/ios` | **8.5.0** |
| `@capacitor/app` | 8.1.1 |
| `@capacitor/preferences` | 8.0.1 |
| `@capacitor/splash-screen` | 8.0.2 |
| `@capacitor/status-bar` | 8.0.3 |

The four plugins are versioned independently of the core, so `^8.0.0` was never
going to give 8.5.0 for all seven. Harmless in itself — and the reason
**`mobile/package-lock.json` is now committed**. #213's workflow names the missing
lockfile as *"the first thing that would make this job non-reproducible"* and
mitigates by printing resolved versions; with a lockfile it does not have to.

### 1.4 Generating the platform broke a green test, on the machine doing the work

`npm run add:android` — the command `mobile/README.md` instructs — turned
`tools/mobile/shell-invariants.test.mjs` red. `cap copy` writes a **copy** of
`capacitor.config.json` into each platform's native bundle
(`@capacitor/cli`'s `tasks/copy.js` → `copyCapacitorConfig`), and the *"mobile/ is
the only place a Capacitor config lives"* test walks the filesystem, so it counted
the artefact as a second config.

Fixed by skipping the two generated platform directories, **derived from the real
config's own `ios.path`/`android.path`** rather than hardcoded. Nothing about the
hazard is lost: what that test guards is a config somewhere `cap` would read as a
*project* root — the repo root above all, which is where #36's own text tells
people to run `npx cap add` — and a copy inside a platform's own tree is never
read that way. A second test keeps the skip honest by asserting both platform
directories are gitignored in full, so relaxing the ignore rule fails loudly
instead of quietly widening what the walk skips.

Worth naming separately: the *"no generated native config re-enables the
KeepRunning footgun"* test was written to arm for later and matched nothing.
It now walks a real generated `android/app/src/main/res/xml/config.xml` — and
that file, as Capacitor 8.5.0 generates it, contains **no `<preference>` elements
at all**, so `KeepRunning` takes its safe `true` default.

### 1.5 The platform is not committed

Same call as iOS, and now for a second independent reason.

- **iOS.** #213 builds the shell on a macOS runner by running `npm run add:ios`
  *in the job*. `mobile/ios/` is not in the repo and that workflow does not want
  it to be.
- **Android.** ~100 generated files, no reviewer, in a directory that
  **auto-merges with no post-merge review window**. The build being reachable
  here removes the "unverifiable" objection but not the unreviewable one.

`mobile/.gitignore` now ignores `ios/` and `android/` in full, which **reverses
what its own comment used to say** (it argued Capacitor's guidance is to commit
them, and that committing keeps CI simple). The reversal is written into that
file rather than done quietly, because the old argument was not silly — it is
just not the practice the repo settled on twice.

The generate step is reproducible from `mobile/package.json` alone:
`npm install && npm run add:android`. `capacitor.config.json` — the only file in
the chain that carries a *decision* (the app id, the platform paths) — is
committed and pinned by a test.

**What that costs, stated because it is a real loss.** The Android
`res/xml/config.xml` was deliberately left un-ignored so a test could parse the
`KeepRunning` footgun — *an ignored file cannot be checked*. CI no longer sees
that file. But the vector goes away with it: `KeepRunning="false"` can no longer
be **committed**, because the file it would live in can no longer be committed,
and `cap add` regenerates it from a template that sets no preference at all
(§1.4). The guard is now a check on the machine that generated the platform,
which is the machine that builds the APK — so it still runs where it matters. The
committed half of the guard, over the parsed `capacitor.config.json` at any depth
and case-insensitively, is untouched and still runs in CI.

## 2. The CSP verdict: our CSP does not block Capacitor's Android bridge

**Verdict: it does not block it, and there are two independent reasons, either of
which alone is sufficient. This is INFERRED from source and document order, not
measured — §3.**

`docs/mobile-shell.md` §5 states the risk precisely and it was the right worry:
Capacitor Android *"builds `native-bridge.js`, the app's config and the plugin
shims into a string and injects them as an inline `<script>` into the HTML the
local server returns"*, against our `script-src 'self'` with no
`'unsafe-inline'`, which a `<meta>` CSP cannot fix with a nonce. What that
description misses is **when** the injection happens, and on Capacitor 8.5.0 it
also misses that the inline path is no longer the primary one.

### 2.1 The primary path is not an inline script at all

`Bridge.loadWebView()` in the installed `@capacitor/android` 8.5.0
(`capacitor/src/main/java/com/getcapacitor/Bridge.java`):

```java
JSInjector injector = getJSInjector();
if (WebViewFeature.isFeatureSupported(WebViewFeature.DOCUMENT_START_SCRIPT)) {
    String allowedOrigin = Uri.parse(appUrl).buildUpon().path(null)…build().toString();
    try {
        WebViewCompat.addDocumentStartJavaScript(webView, injector.getScriptString(), Collections.singleton(allowedOrigin));
        injector = null;
    } catch (IllegalArgumentException ex) {
        Logger.warn("Invalid url, using fallback");
    }
}
localServer = new WebViewLocalServer(context, this, injector, authorities, html5mode);
```

`injector = null` is the whole point: when the WebView supports
`DOCUMENT_START_SCRIPT`, the local server is constructed with **no injector**, and
every one of `WebViewLocalServer`'s four `getInjectedStream` call sites is
null-guarded. Capacitor's own doc comment on `getJavaScriptInjectedStream` says
so outright — *"This method only changes the original `InputStream` if `WebView`
does not support the `DOCUMENT_START_SCRIPT` feature."* `androidx.webkit`
**1.14.0** is in the generated `variables.gradle`, which is why the feature is
there to be supported.

So on any WebView that supports the feature, **no `<script>` element is ever
created and our HTML is never rewritten.** The bridge is installed by the
embedder before the document exists. There is no document, and therefore no
policy, for `script-src` to be read out of yet.

Two supporting facts read from the same package, both of which the scaffold had
assumed rather than checked, and both of which hold:

- `CapConfig.java` defaults: `hostname = "localhost"`,
  `androidScheme = CAPACITOR_HTTPS_SCHEME`. So the Android origin really is
  **`https://localhost`**, as `docs/mobile-shell.md` and
  `shouldRegisterServiceWorker`'s comment both say.
- `native-bridge.js` (1,039 lines, read in full for this) contains **no `eval`,
  no `new Function`, no `createElement`, no `innerHTML`, no `Blob`, no `Worker`
  and no `importScripts`**. Its transport is a `@JavascriptInterface` object
  (`androidBridge.postMessage`), which CSP does not govern at all. Its `fetch`
  and `XMLHttpRequest` patches are gated behind `CapacitorHttpAndroidInterface.isEnabled()`
  and our config does not enable `CapacitorHttp`, so they do not run. **There is
  no CSP-governed operation in the bridge beyond the script's own execution.**

### 2.2 The fallback path also escapes, for a different reason

If `DOCUMENT_START_SCRIPT` is unsupported, `injector` survives and
`JSInjector.getInjectedStream` rewrites the HTML — exactly as §5 described. It is
still not blocked, and this is the reason the verdict does not depend on which
path runs:

```java
if (html.contains("<head>")) {
    modifiedHtml.insert(html.indexOf("<head>") + "<head>".length(), "\n" + js + "\n");
```

The script goes in **immediately after `<head>`**. In our `index.html`, `<head>`
is on **line 3** and the CSP `<meta>` is on **line 22**. A policy delivered by
`<meta http-equiv>` is enforced from the moment the parser processes that
element; content earlier in the document is not governed by it, which is the
whole reason the advice is to put a meta CSP first in `<head>`. The injected
script therefore parses and executes nineteen lines before our policy exists.

Note this is not a latent fragility we should be relieved about — it is
**structural**. Capacitor inserts at `indexOf("<head>")`, so the injected script
is always the *first* thing in the head, ahead of anything we could put there. We
could not move our CSP in front of it even if we wanted to.

### 2.3 What follows, and one risk that closes with it

`window.Capacitor` exists on Android, so:

- All four installed plugins (`app`, `preferences`, `splash-screen`,
  `status-bar`) can work. None is registered by our code yet, but nothing
  structural blocks them.
- **The service-worker degradation in `docs/mobile-shell.md` §5 does not arise.**
  That section's second consequence was that `shouldRegisterServiceWorker` would
  see no bridge and an ordinary `https://localhost` origin, register `sw.js`
  inside the shell, and hand us the "app won't update after a store release" bug.
  With the bridge alive, `isNativePlatform()` answers `true` and the worker stays
  off. Android has only ever had **one** of the two signals — the origin check
  cannot help there, deliberately, because a hostname test would break the
  offline shell for anyone serving the real site from a local dev server — so it
  is worth being explicit that the surviving signal is the one that matters, and
  that a future Capacitor release which drops or renames `isNativePlatform` takes
  Android's only signal with it.
- No CSP token needs adding, and none of `docs/mobile-shell.md` §5's two
  "if it does bite" options — serving the CSP as a response header, or
  configuring the bridge to be served as a file — is needed. Both were changes to
  the shell's *shape*; neither is now on the table.

## 3. What §2 is worth, and what would settle it

**§2 is an inference. It is a good one, and it is not a measurement.** Two
mechanisms in Capacitor's Java, one fact of document order in our own markup, and
the CSP specification's rule about when a meta-delivered policy begins to apply.
No WebView executed anything. Specifically **not** claimed: that a running
Android app logs zero CSP violations.

#213 measured that on **iOS**, where the mechanism is `WKUserScript` and the origin
is `capacitor://localhost`; §2's whole point is that Android's mechanism is
different, so that result does not transfer and neither does this one in reverse.
**And #213's own scope is narrower than it is easy to remember:** the
0-CSP-violations reading comes from a booted **iOS Simulator**, and its arm64/Release
step is a **compile only** — `BUILD SUCCEEDED`, unsigned, never installed, never
launched. `docs/ios-ci.md` twice warns that a simulator is not a device. So "the
bridge survives our CSP" is observed on one simulator, inferred on Android, and
unobserved on real hardware of either kind. An earlier draft of this change
compressed that into "on both a simulator and an arm64 device" in
`docs/mobile-shell.md` §5; the reviewer pass caught it and it is fixed.

**What settles it, cheapest first.** All three are `HUMAN-ACTIONS.md` item **#18**
in the post-#220 numbering, which this document deliberately does not edit
(#220 renumbered 46 references across 7 files and is `MERGEABLE`, waiting only on
a founder label).

1. **A phone over USB, ~5 minutes, no Android Studio and no emulator.**
   `adb install app-debug.apk`, then `chrome://inspect` on the desktop, and read
   three things off the console: any CSP violation, `typeof window.Capacitor`,
   and `navigator.serviceWorker.controller` (must be `null`). This is the version
   `docs/mobile-shell.md` §6 already asks for and it is still the right one.
2. **`adb logcat` alone**, if `chrome://inspect` is inconvenient. A blocked
   inline script logs a console message that WebView forwards to logcat, and the
   absence of one across a launch is weak but real evidence.
3. **A CI job.** Not added here, on purpose: `.github/` is a governed path
   needing a founder label, and the build should be proven locally first — it now
   is. If someone wants it, the shape is `ubuntu-latest`, no emulator:
   `npm install` → `npm run add:android` → `./gradlew assembleDebug` +
   `assembleRelease`, with `actions/setup-java` at **21** and
   `android-actions/setup-android`, on `workflow_dispatch` plus a path filter over
   `mobile/**`, `tools/mobile/**`, `index.html`, `app.js` and `player/**`. It
   proves §1 keeps holding and it **cannot** prove §2 — a build is not a launch,
   and MP1 §6.2/§6.4 are the reason not to reach for an emulator to close that
   gap. It must not become a required check.

## 4. `navigator.mediaSession` — still inferred, and MP1 §5.4 overstates it

**Not measured here.** Settling it needs execution in the shipped WebView, and
this machine cannot reach a WebView (§0). The claim stands exactly where MP1 left
it: **source-derived**.

The source is strong. `android_webview/lib/aw_main_delegate.cc` appends
`switches::kDisableMediaSessionAPI` with the comment *"WebView does not support
MediaSession API since there's no UI for media metadata and controls"*, and
WebView's own `not-webview-exposed.txt` lists `getter mediaSession` and
`interface MediaSession`. Nothing in this build can change it: the switch is
appended by the WebView provider's own main delegate, not by the embedding app,
so there is no Capacitor config, `gradle.properties` line or manifest flag that
turns it back on. Reading `@capacitor/android` 8.5.0 for this build turned up
nothing that touches it either.

**One correction now MADE in `docs/research/mp1-background-audio.md`.** §5.4 ended
*"Confirmed live: the spike logs `mediaSession present=` on startup — see §6"* — and
§6 says the spike **never ran** and not one line was ever logged. The sentence
described an instrument, not a result, and it was the only place in that document
where an Android claim looked measured. This change was originally going to leave it
alone because #220 had that file open; **#220 has since merged**, so it is fixed here
instead, and the replacement says plainly that the claim is source-derived and what
would close it.

**The consequence, unchanged and still the biggest scope item in MP1.** #27
(lock-screen and steering-wheel controls) **cannot be delivered in the Android
shell from JS at any price.** `player/media-session.js` is not wasted — it works
in mobile browsers, and #28's native backend needs the same metadata mapping — but
it buys the Android *app* nothing. On Android those controls are native work, and
§5 explains why they and the foreground service are the same piece of work.

## 5. The foreground service, given #227 — reasoning, not a verdict

**Not built, and deliberately not decided.** #227 (`c1c4e69`) changes the inputs
enough that MP1's Android §5.3 should not simply be re-quoted, and not enough to
answer the question. Both halves below matter.

### 5.1 What #227 changes, and it is more than it looks

Before #227, a cross-episode seam was **measured at 9,153 ms of silence**
(STATE.md, run 32036295743): the boundary paused the element, the page stopped
being audible, and only then did the next segment load. #227 loads the next
segment on a second `<audio>` element **while the current one is still audible**,
and pauses the outgoing element only after the incoming one is `canplay`. The
silent window drops to the authored **2.0 s** beat.

That matters here specifically because **audibility is the currency the whole
Android argument is denominated in** — and be careful which half of that is
measured, because MP1 keeps them apart. **Measured** (§4, desktop Chromium, the
same engine as Android WebView): a hidden page's timers collapse the moment the
element pauses and are left alone — 111 ms median for a 100 ms timer, identical to
visible — while it stays audible. **Source-traced, not measured** (§5.2): that
Blink exempts an audible page from *freezing* as well, and the 30 s grace after
audio stops (`kRecentAudioDelay`, whose source comment reads *"A page cannot be
throttled or frozen 30 seconds after playing audio"*) — a constant read out of
Chromium, not a stopwatch reading. The app spends
**5–11 s** of that 30 s window at every one of Foray #1's **16 cross-episode
seams**, with a JS timer inside it that has to fire for the Foray to continue.

> **RETRACTED 2026-08-17 — this paragraph used to say #227 cut that to 2.0 s.**
> #227 was measured on a device making the seam WORSE (the segment was dropped,
> not shortened) and is parked default-off. Its premise was that warming in the
> audible window dodges the throttle; the throttle on media-element load tasks is
> keyed to VISIBILITY, not audibility (MP1 §4.1a). So the seam is back to its
> measured 5–11 s and **the engine-level case for a foreground service is at full
> strength, not weakened.**
>
> What DID land is the cliff, not the slack: 9,153 ms was **92% of
> `LOAD_SETTLE_TIMEOUT_MS`**, past which `load()` rejects and the segment is
> **dropped** — MP1 §4.4 measured 3 of 5 hidden-page Chromium loads already
> failing exactly that way. That deadline is visibility-aware as of 2026-08-17
> (10 s visible, **20 s hidden**), so a slow seam no longer drops a segment. It
> does not make the seam shorter, and on Blink it now spends up to ~20 s of the
> 30 s grace rather than 10 s — which is the right trade for a dropped segment,
> and a point IN FAVOUR of a foreground service rather than against one.

Three limits on that, because the improvement is not uniform:

- **Same-episode seams are deliberately not warmed** — 15 of Foray #1's 31. They
  do not need it: `load()`'s same-source seek keeps the buffer.
- **A bridged seam gets no warming at all**, and neither does the load *after* it,
  because by then the bridge is the current item. `seamGapSec` returns 0 for a
  bridge, which is the eligibility test. Neither shipped Foray has narration, so
  this is theory today — but the moment one does, those seams revert to the old
  cost.
- **Losing the race costs exactly what today costs.** If the warm element is not
  ready at the out-point, `load()` takes the identical path. A cold start, a
  slow CDN or a throttled process can still produce the old 9 s window.

### 5.2 What #227 does not touch, and this is the half that decides it

A foreground service on Android is not, in the end, about the length of our
silences. It is about two things at a layer above Blink, and #227 is invisible to
both.

- **The Android 15 audio-focus rule.** *"If an app targets Android 15 (API level
  35) or higher, it cannot request audio focus unless it's the top app or running
  a foreground service."* Capacitor 8.5.0 generates `targetSdkVersion = 36`
  (§1.2), so **we are inside this rule from the first build** — measured, from the
  generated `variables.gradle`. This is about *requesting* focus, and #227 does
  not reduce the number of requests: every seam still ends in a `play()`, and
  after #227 it ends in a `play()` on **a different element making its first
  sound**. If anything, the prefetch design gives the rule one more surface, not
  fewer. **Whether it bites at all is unverified and the uncertainty runs both
  ways**, which is why this is not a verdict: WebView's participation in Android
  audio focus for plain `<audio>` is not something this repo has established. If
  WebView does not request focus, the restriction cannot deny us — but then our
  audio also does not duck for a phone call and is not paused when another media
  app takes over, which is its own defect. If it does request, an FGS is the only
  way a backgrounded Foray keeps getting focus. Both branches are real and only a
  device tells you which one you are in.
  One trap for whoever measures it: **#227's two safety nets cannot tell these
  apart from JS.** An autoplay-policy refusal, an audio-focus denial and "a
  `pause` nobody asked for" all arrive as a rejected `play()` or an unexplained
  `pause`, and #227 recovers the first and stops warming on the third. A run that
  reports "warming stopped for the session" is not evidence about which mechanism
  fired.
- **Process importance.** The documented importance ladder is foreground →
  visible → service → cached; a cached process is moved into a frozen cgroup
  where *"all of its threads are suspended"*. `startForeground()` confers
  *visible*. **Playing audio appears nowhere on that ladder.** MP1 §5.3 is
  careful to label "a `mediaPlayback` FGS prevents freezing" as an *inference*
  from those two facts, and that inference is untouched by how long our seams
  are. Neither are OEM battery managers, which MP1 §6.4 notes are untestable on
  any emulator by construction.

And a third reason that is not about audio surviving at all: **an FGS is the only
vehicle on Android for the controls §4 says we cannot get from JS.** No
`mediaSession`, no notification, no lock-screen or steering-wheel controls — and
`04_VOICE_AUDIO_SPEC.md` calls those *"the baseline hands-free interface"* that
*"must be flawless before any voice work"*. So even in the best case where #227
plus Blink's grace window keeps the audio alive unaided, the Android shell still
owes native work. The FGS and #27's Android half are one job, not two, and MP1
§5.5's plugin table is the menu: fork a Capacitor-6-era `mediaSession` polyfill
forward, bolt a generic FGS on and still write the notification natively, or do
#28's Android half properly.

### 5.3 The honest summary

#227 makes the *engine-level* argument for a foreground service materially
weaker and probably removes Blink throttling mid-seam as a practical failure
mode. It does not touch the *OS-level* arguments, which are the ones MP1 §5.3
identified as *"where the shell actually fails"*. **I am not claiming it either
way**, and nothing short of the following claims it either:

A real phone, **off charger**, app backgrounded and screen locked, playing a
Foray across at least two **cross-episode** seams and — once narration exists —
one **bridged** seam, on stock Android and separately on a Samsung or Xiaomi
device. Logging must distinguish "JS stopped" from "audio stopped", which is what
MP1 §6.1's intended method already does with a 1 Hz heartbeat reporting both its
own interval and how far the playhead moved. An emulator cannot answer this: MP1
§6.4 lists Doze, the cached-app freezer, OEM managers, real audio focus and
Bluetooth routing as the five things it does not model, and they are the five
things the question is made of.
